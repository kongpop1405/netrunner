กระโดดถี่ขึ้น — ลด jump gap 3s → ~1s

netrunner · CookieRun · ไม่ต้อง detect หลุม — แก้ที่โครงสร้าง loop

ทำไมเลิกไล่ pit detection: วัดจากจอจริงแล้ว หลุมโผล่ขอบขวา→ถึงตัวคุกกี้ ใช้เวลาน้อยกว่า 1 เฟรม (screencap 856 ms). Detector ที่เขียนเสร็จแล้ว ทดสอบกับ run เต็ม ep1 (118 เฟรม): เตือนก่อนตก 0 ครั้ง, เตือนหลังตายไปแล้ว 10 ครั้ง. ที่ latency ระดับนี้ ไม่มี algorithm ไหนช่วยได้ — แต่ความถี่การกระโดดช่วยได้ และวัดได้ชัด

Probe chain ไม่ได้กิน grab (engine reuse frame ใน pure-goto chain อยู่แล้ว) — ตัวกินคือ grab 2 ครั้ง + sleep. และ probe chain ทั้งหมดมีเหตุผลอยู่ที่ หลัง run จบ (popup รางวัล/friend) ไม่ใช่ระหว่างวิ่ง.

Dสิ่งที่จะแก้

1. device.py — persistent adb shell

เปิด adb shell ค้างไว้ ส่งคำสั่งทาง stdin. tap 45 ms → 9.5 ms (วัดแล้ว). ล้มเหลว → fallback เป็น spawn เดิม.

2. fsm.py — "no_poll_sleep": true ต่อ state

ข้าม sleep(poll_ms) เฉพาะ state ที่ประกาศไว้ (in-run เท่านั้น). ประหยัด 600 ms/รอบ. State อื่นไม่กระทบ.

3. cookierun.json — in-run fast loop

guard_not_shop.on_absent → jump + goto running (ตรง ๆ ไม่ผ่าน probe chain). Probe chain ยังอยู่ครบ แต่เข้าถึงจาก check_shop_after_run ซึ่งวิ่งเฉพาะตอน running timeout / result เจอ.
เหลือ grab เดียวต่อรอบ: 856 ms + jump 10 ms ≈ 0.9 s/jump

4. act.py — double_jump_chance ตั้งค่าได้ต่อ action

หลุมกว้างต้อง double jump. ให้ config สั่ง "double": 1.0 ระหว่าง run ได้ (ปัจจุบัน hardcode 35%). ต้อง A/B วัดจริง — double เสมออาจทำให้ข้ามแพลตฟอร์มเตี้ยพลาด.

!ความเสี่ยง / กติกาที่คงเดิม

  • ความเสี่ยงหลัก: ตัด probe chain ออกจาก in-run loop → popup ที่โผล่ระหว่าง run (friend info จาก relay tap หลง) จะไม่ถูกเก็บทันที. บรรเทาโดย running.timeout_ms ยังพาไป guard_not_home → chain เดิมทั้งชุด
  • Relay tap (960,540) ยังอยู่ แต่ตอนนี้ยิงถี่ขึ้น → โอกาสโดน leaderboard มากขึ้น. ทางแก้: ยิง relay ทุก N รอบ ไม่ใช่ทุกรอบ
  • ทุก safety net เดิม (coin guard, heart gate, ห้าม gem, probe chain) ไม่ลบทิ้ง — แค่ย้ายจุดเรียก
  • วัดผลด้วย: jump gap median (log), และ Play-to-Play interval — ไม่ใช่ความรู้สึก
